--------------------------------------------------------------------------------
3. WHY threads=1 BEATS threads=2 (the counter-intuitive result)
--------------------------------------------------------------------------------

threads=2 IS genuinely faster at pure inference, even under load: 28.8-31.0 ms
vs 38.5-40.3 ms. It also wins slightly on end-to-end pipeline rate
(18.1-19.3 Hz vs 16.5-17.4 Hz). So why not use it?

Because the extra ~1.7 Hz costs:
  - 72% more CPU in policy_node (149.8% vs 87.0%)
  - nearly all remaining system headroom (idle 1.0% vs 8.5%)
  - measurably worse actuation RTT (avg +3 ms, max +9 ms)

And it buys almost nothing physically. At the policy's 0.1 m/s forward
setpoint:
    17.0 Hz -> 5.9 mm of travel between control updates
    19.0 Hz -> 5.3 mm
A 0.6 mm difference. Not worth spending the entire CPU reserve and degrading
the safety-critical path.

A second-order effect is visible in the data and worth understanding: with
threads=2, decode and preprocess get SLOWER (decode ~14 ms vs ~11 ms,
preprocess ~10 ms vs ~8.2 ms). ONNX Runtime's extra worker threads are
competing with the same process's own single-threaded OpenCV decode/resize
work. The ONNX pool steals CPU from the pipeline stages feeding it, which is
why doubling inference threads yields far less than a proportional speedup.

--------------------------------------------------------------------------------
4. ISOLATED BENCHMARKS DO NOT PREDICT CONTENDED PERFORMANCE
--------------------------------------------------------------------------------

Standalone benchmark_inference ranking:
    ORT default : 9.92 ms   (best)
    threads=2   : 13.99 ms
    threads=1   : 26.05 ms  (worst)

Full-stack ranking (by RTT and headroom):
    threads=1   : best
    threads=2   : middling
    ORT default : worst (235% CPU, 0.6% idle)

The ranking INVERTS completely. With four free cores, more threads win. With
six CPU-hungry processes sharing four cores, a bigger thread pool just means
policy_node fights harder with everything else -- including its own decode
stage. Always re-measure under the full graph before trusting a tuning
decision. This mirrors the earlier Cyclone-vs-FastDDS result on this same
board, where the "better" option in principle was worse in practice.

--------------------------------------------------------------------------------
5. BUG FOUND WHILE ANALYSING THESE NUMBERS: policy staleness timeout
--------------------------------------------------------------------------------

safety_arbiter originally guarded /policy/cmd with teleop_timeout_s (0.15 s).
But the two streams differ by an order of magnitude in rate:
    teleop/cmd  : 50 Hz  -> 20 ms period
    policy/cmd  : ~17 Hz -> 59 ms period, 119.1 ms worst case measured

That left roughly 30 ms of margin. One slow inference frame -- well within
observed jitter -- would have tripped a spurious FAILSAFE mid-autonomous-drive.

FIXED: added a separate policy_timeout_s, default 0.30 s (~5 policy periods,
~2.5x worst-case observed latency). Re-tune if model size or resolution
changes.

--------------------------------------------------------------------------------
6. WHERE THE TIME ACTUALLY GOES (recommended config)
--------------------------------------------------------------------------------

    JPEG decode      ~11 ms   (19%)
    crop + resize     ~8 ms   (14%)
    ONNX inference   ~39 ms   (67%)
    ------------------------------
    total            ~58 ms   -> ~17 Hz

Inference dominates, but decode+preprocess together are ~19 ms -- a third of
the inference cost, and not negligible. Two future levers if more rate is
needed:
  (a) Lower camera resolution below 640x480. Cuts decode cost directly. The
      policy only consumes 160x120 anyway. CAVEAT: verify FOV is preserved --
      some UVC modes crop rather than bin, and peripheral vision matters more
      to a path-following policy than resolution does.
  (b) Convert ONNX -> LiteRT/TFLite + XNNPACK. This was the runtime the
      original design research recommended for this chip; ONNX Runtime CPU was
      chosen here only because it required no conversion step. XNNPACK ships
      Cortex-A53-tuned microkernels and may beat ORT meaningfully. UNTESTED --
      worth measuring before assuming.

--------------------------------------------------------------------------------
7. SAFETY MARGIN ASSESSMENT
--------------------------------------------------------------------------------

  MCU watchdog trip threshold          : 150 ms
  Worst observed RTT (recommended cfg) :  52.5 ms
  Margin                               : ~2.9x

Acceptable, but this is not comfortable margin, and it degraded from a 2.24 ms
baseline purely from CPU contention. MONITOR the hardware_bridge RTT line
during every autonomous session. If RTT max starts approaching ~100 ms,
stop and reduce load (lower max_inference_hz, or disable the recorder for
non-data-collection runs) before continuing.

Note also that with no physical e-stop on this vehicle, the deadman release is
the primary interlock. It is a software path, and it depends on this same
contended CPU. That is a further argument for keeping the 8.5% idle headroom
rather than spending it on 1.7 Hz.

--------------------------------------------------------------------------------
8. WHAT THIS SAYS ABOUT THE UNO Q AS AN INFERENCE PLATFORM
--------------------------------------------------------------------------------

A PilotNet-class CNN (~250k params, 120x160 input) runs at ~25 Hz pure
inference and ~17 Hz end-to-end alongside a full ROS 2 control graph, on CPU
alone, with no NPU. That validates the original architecture decision to keep
the policy tiny.

For calibration: the design research anchored on DeepPicar's 18.49 ms/frame
for a comparable net on a Cortex-A53 @ 1.2 GHz. Isolated, this board hit
9.92 ms -- consistent with a faster clock and a better runtime. Contended, it
is 38-40 ms. The gap between those two numbers IS the finding: on a 4-core SBC
running a real robot stack, inference cost roughly quadruples versus a clean
benchmark. Any future model-size decision should budget against the contended
number, not the isolated one.

There is no headroom here for a MobileNet-class backbone, confirming the
earlier decision to train PilotNet from scratch rather than fine-tune a
pretrained ImageNet model.
